# Autobot ↔ Axiom Bridge

Autobot generates apps. [Axiom](https://github.com/CharlesWiltgen/Axiom) audits them.
This skill wires the two together at exactly two seams so Autobot inherits Axiom's
domain coverage without inheriting a hard dependency.

## When to use

| Trigger | Caller | Mode |
|---------|--------|------|
| Phase 5 Step 7 — build just succeeded, *before* Gate 5→6 check | `quality-engineer` | **Critical auditors only** (block on Sev: critical) |
| Phase 7 retrospective — data collection step | `autobot-retrospective` | **Full health-check** (report-only, never blocks) |

Both modes **soft-skip silently** when Axiom is not installed — Autobot must
keep working standalone.

## Detection (must run first)

```bash
AXIOM_ROOT=$(bash "$CLAUDE_PLUGIN_ROOT/scripts/detect-axiom.sh" 2>/dev/null || true)
if [ -z "$AXIOM_ROOT" ]; then
  # Soft skip — log and continue. detail.reason is required by logEvents.detailSchema.
  bash "$CLAUDE_PLUGIN_ROOT/scripts/build-log.sh" \
    --phase "$PHASE" \
    --event axiom_audit_skipped \
    --detail '{"reason":"axiom_plugin_not_installed","mode":"'"$MODE"'"}'
  exit 0
fi
```

Both events are registered in `spec/pipeline.json.logEvents`:
- `axiom_audit_skipped` — `detail.reason` required, `detail.mode` optional.
- `axiom_audit_completed` — `detail.mode` and `detail.criticalCount` required;
  `auditors`, `warningCount`, `findingsPath` optional.

If `AXIOM_ROOT` is set, the Axiom plugin and its agents are loaded in this
Claude Code session (both plugins share `~/.claude/plugins/cache/`), so you
invoke its agents directly with the `Task` tool — no shell-out, no slash
command, no parsing.

## Mode 1: Gate-5 Critical Audit (Phase 5)

**Goal**: catch runtime-fatal issues that compile cleanly. Block Gate 5→6 if
any *critical*-severity finding is reported.

**When**: in `autobot-integration-build` Step 7, after `BUILD SUCCEEDED` and
before recording `phases.5.metadata.build_succeeded`.

**Critical auditors** — run in parallel via a *single* message with one `Task`
tool call per auditor:

| Auditor (subagent_type) | Why it's Gate-5 critical |
|-------------------------|--------------------------|
| `axiom:concurrency-auditor` | Swift 6 data races → silent corruption / runtime crash |
| `axiom:swiftdata-auditor` | Schema/relationship mistakes → permanent data loss |
| `axiom:memory-auditor` | Timer/observer/closure leaks → background OOM |
| `axiom:swiftui-architecture-auditor` | `@State`/`@Observable` misuse → wrong-thread updates |

**Prompt template** (per auditor):

```
Audit the iOS app at <AppName>/ generated by Autobot.
Scope: <AppName>/Views, <AppName>/ViewModels, <AppName>/Services, <AppName>/App.
DO NOT scan <AppName>/Models — those are an immutable type contract (SSOT).
Report findings as JSON: {"critical": [...], "warning": [...], "info": [...]}.
Each finding: {file, line, rule, message, fix_hint}.
Be terse — Autobot will route fixes mechanically.
```

**Result handling**:

```python
critical = sum(len(r["critical"]) for r in auditor_results.values())
build_state.phases["5"].metadata["axiom_critical_audit"] = {
    "ran": True,
    "auditors": list(auditor_results.keys()),
    "critical_count": critical,
    "findings_path": ".autobot/axiom-critical.json",  # MUST exist on disk for the gate
}
```

The `findings_path` file (JSON with full auditor output) **must be written
to disk** before the gate runs — `axiom_critical_audit_acceptable` checks
its existence and rejects PASS without artifact. Also append a structured
log event:

```bash
bash "$CLAUDE_PLUGIN_ROOT/scripts/build-log.sh" --phase 5 \
  --event axiom_audit_completed \
  --detail '{"mode":"critical","criticalCount":0,"auditors":["concurrency","swiftdata","memory","swiftui-architecture"],"findingsPath":".autobot/axiom-critical.json"}'
```

- `critical_count == 0` → record and proceed to Gate 5→6.
- `critical_count > 0` → enter the existing Build-Fix Loop (Step 3) with the
  findings as the next batch of errors. Do **not** flip
  `phases.5.metadata.build_succeeded = true` yet. Follow each auditor's
  `fix_hint`. After fixes, re-build, re-run **only the auditors that reported
  critical** (not the full suite).
- Hit Step 3's `max_build_fix_attempts` (5) on auditor findings → record a
  Phase-5 failure with `reason: axiom_critical_unresolved` and let the
  pipeline circuit-breaker take over (skip to Phase 7).

**`Models/` exception**: if an auditor flags something *inside* `Models/`,
treat it the same way the integration-build skill already treats
Models/-rooted errors — fix the *call site*, not the type contract.

## Mode 2: Phase-7 Health-Check (Retrospective)

**Goal**: a wide, non-blocking inventory of every domain-level issue in the
shipped/abandoned build, fed back into `learnings.json` so the next build
prevents what this build caught.

**When**: in `autobot-retrospective` data collection, *after* build metrics
are gathered.

**Single dispatch** — Axiom's `axiom:health-check` agent orchestrates all
auditors itself, deduplicates findings, and produces a unified report. One
`Task` call is enough:

```
subagent_type: axiom:health-check
prompt: |
  Run the full Axiom health-check on <AppName>/.
  Exclude <AppName>/Models (immutable contract) and <AppName>Tests.
  Write the unified findings JSON to .autobot/axiom-health.json.
  Return a one-paragraph executive summary.
```

**Result handling**:

1. Write the executive summary into `build-report.md` under a new section
   `## Axiom Health-Check`.
2. For every distinct `rule` that appears ≥ 1 time, increment
   `learnings.json` → `patterns.axiom_findings[rule].frequency` (initialize
   if absent). This is the same shape used for `common_build_errors` so the
   Phase-0 learning bootstrap picks it up automatically.
3. Record:
   ```json
   build_state.phases["7"].metadata["axiom_health_check"] = {
     "ran": true,
     "findings_path": ".autobot/axiom-health.json",
     "summary_path": "build-report.md#axiom-health-check"
   }
   ```

**Never block on Phase-7 findings.** Phase 7 exists to learn, not to gate.

## Soft-skip contract (both modes)

When `detect-axiom.sh` exits non-zero, the bridge must:

1. Log one `axiom_audit_skipped` event to `build-log.jsonl`.
2. Record `metadata.axiom_*.ran = false` on the current phase.
3. Return success. The build proceeds exactly as if this skill did not exist.

The user is **not** prompted to install Axiom mid-build. Setup-time discovery
(`/autobot:setup`) is the right place to surface the recommendation.

## Why two seams, not one

- Gate 5 is the last point where Autobot still has the model loaded, the
  build green, and the fix loop primed — fixing critical findings here costs
  one extra build cycle. Pushing them to Phase 7 means they ship.
- Phase 7 is the only place wide enough to absorb the full health-check
  without ballooning Phase-5 wall-time. Treating *every* finding as critical
  would turn every build into an audit marathon.

## Anti-patterns

- ❌ Calling `axiom:health-check` in Phase 5. It runs every auditor; Gate 5
  only needs the four that catch runtime-fatal classes.
- ❌ Shelling out to `/axiom:audit` or `/axiom:health-check`. The slash
  commands are for humans; subagent dispatch keeps the result structured.
- ❌ Treating Phase-7 findings as build failures. Use them to seed
  `learnings.json`, not to retroactively fail a finished build.
- ❌ Auditing `<AppName>/Models/`. The architect's contract is SSOT — fix
  call sites instead, even when the auditor points at the type.
