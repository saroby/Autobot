# SSOT 청사진 문서 템플릿

`autobot-ssot` 가 생성하는 문서의 표준 구조. 섹션 이름은 계약이다 — 병합·재개 로직이 헤딩으로 위치를 찾는다. **내용이 없는 섹션·파일은 만들지 않는다** (빈 헤딩 금지). 파일 세트는 상한이지 고정 스캐폴드가 아니다.

## ssot/README.md — 청사진 인덱스 (status 소유)

```markdown
---
status: interviewing | confirmed | blueprinted
updated: <YYYY-MM-DD>
---

# <제품 이름> — 청사진 (SSOT)

> <제품 한 문장 — 누구의 어떤 문제를 어떻게 푸나>

이 폴더는 제품의 정수다. 코드를 잃어도 이 문서들로 같은 제품을 다시 만들 수 있어야 한다.

## 문서
| 파일 | 소유 |
|------|------|
| product.md | 왜 존재 — 문제 · 유저 · 차별화 · 성공 지표 |
| features.md | 무엇을 — 기능 세트와 MVP 경계 |
| domain.md | 핵심 개념 — 엔티티 · 용어집 |
| principles.md | 원칙 · 하지 않을 것 · 제약 |
| design.md | 성격 · 톤 · 디자인 방침 |
| decisions.md | 결정 로그 (경량 ADR) |

## 이 청사진으로 재빌드하는 법
1. 새 프로젝트에서 `git submodule add <이 repo url> ssot`
2. `ssot/product.md` → `ssot/features.md` 순으로 읽어 MVP 스코프를 잡는다.
3. `ssot/domain.md` 로 데이터 모델을, `ssot/principles.md` 로 하지 않을 것을 고정한다.
4. 화면 단위 기획은 `/autobot:screen` 으로 이어간다.
```

status 전이: `interviewing`(R1–R5 진행 중) → `confirmed`(R6 승인) → `blueprinted`(submodule 배선 완료).

# 루트 SSOT — `ssot/` 를 가리키는 얇은 문서

`ssot/` 가 정본이다. 루트 3종은 그 위에 얹히는 증류본·포인터다. 중복을 최소화한다.

## SOUL.md — 제품 정체성 (증류본)

```markdown
# <제품 이름>의 영혼

> <제품 한 문장 — 누구의 어떤 순간을 어떻게 바꾸나>

## 누구의 어떤 순간
<핵심 유저와 그들이 제품을 여는 순간·감정>

## 차별화 한 방
<이 제품을 대체 불가능하게 만드는 것>

## 하지 않을 것
- <의도적으로 배제하는 것>

> 정본 청사진: `ssot/` (product.md · principles.md · …)
```

## AGENTS.md — 에이전트 작업 규칙 (정본)

```markdown
# AGENTS

이 프로젝트에서 작업하는 모든 에이전트의 규칙. CLAUDE.md 는 이 파일을 참조한다.

## SSOT 지도
| 문서 | 소유 |
|------|------|
| ssot/ | **제품 청사진** — 왜·무엇·도메인·원칙. 재빌드마다 재사용 (git submodule) |
| SOUL.md | 제품 정체성 증류본 |
| docs/screens/<slug>.md | 화면별 spec — 무엇·어떻게 (`/autobot:screen`) |
| AGENTS.md | 작업 규칙 — 이 파일 |

## 규칙
1. 기능·데이터 모델을 만지기 전에 `ssot/` 를 먼저 읽는다 — 청사진이 진실이다.
2. 청사진과 코드가 어긋나면 `ssot/` 를 진실로 본다 (청사진이 틀렸으면 청사진부터 고친다).
3. 제품 수준 결정이 바뀌면 `/autobot:ssot` 로 청사진을 갱신한다 — 청사진 밖에서 몰래 결정하지 않는다.
4. 화면 코드는 `/autobot:screen` 인터뷰로 시작 — spec 없는 화면 코드 금지.
```
